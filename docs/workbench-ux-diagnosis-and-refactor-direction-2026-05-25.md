# 工作台使用问题诊断与修改方向（2026-05-25）

## 1. 当前问题描述

AgentThee 当前已经具备比较完整的底层能力：

- 工作区
- 会话
- 任务
- 工作流
- 产物
- Trace
- 记忆
- 模型配置
- 插件
- 结果沉淀

但从用户使用角度看，它现在更像一个 **Agent 运行状态控制台**，而不是一个自然可用的 **个人 Agent 工作台**。

用户打开后会直接看到大量内部对象和流程状态，例如：

- Run
- Node
- Evidence
- Artifact
- Trace
- Runtime
- Binding
- Workflow
- Backflow

这些概念对研发和调试有价值，但对真实用户来说，第一反应可能是：

```text
我现在应该做什么？
它有没有真的在帮我干活？
我需要点 Advance 还是 Complete Node？
为什么我提交需求后只是出现一堆流程节点？
```

所以当前主要矛盾不是“没有架构”，而是：

```text
系统把内部机制直接暴露给用户了，缺少一层面向人的任务体验封装。
```

## 2. 核心修改目标

将产品从：

```text
Agent 状态机可视化控制台
```

调整为：

```text
用户提交复杂任务后，可以持续推进、随时恢复、清楚知道下一步该做什么的个人 Agent 工作台
```

底层仍然可以保留 Run / Node / Artifact / Trace，但前台不应该让用户围绕这些术语操作，而应该围绕以下用户心智来组织：

- 任务
- 进展
- 阻塞
- 结果
- 继续

## 3. 修改方向一：重构首页和工作台入口

当前入口偏弱，工作区选择、初始化、最近工作区、进入工作台之间有割裂感。

建议改成：

- 首页默认展示“最近工作区 + 最近任务 + 继续入口”
- 打开目录时，如果不是工作区，自动提示“创建为工作区”
- 进入工作台后必须有明确状态：
  - 没有工作区：引导打开 / 创建
  - 有工作区但没模型：引导配置模型
  - 有模型但没任务：引导输入第一个任务
  - 有进行中任务：突出“继续任务”
  - 有阻塞任务：突出“需要你处理”

首页不应该只是目录列表，而应该成为用户回来的“续作入口”。

## 4. 修改方向二：降低主界面的系统术语

当前主界面信息太像研发验收页。建议第一层只保留用户能理解的对象：

- 当前任务
- 当前进度
- 下一步
- 需要我确认的事项
- 已产生的结果
- 历史记录 / 证据

内部概念建议降级：

| 当前表达 | 建议表达 |
| --- | --- |
| Workflow board | 任务步骤 |
| Execution timeline | 最近进展 |
| Evidence panel | 详情 |
| TaskRuntime | 高级调试信息 |
| Trace | 过程记录 |
| Artifact | 产出 |

这样用户不会觉得自己在操作一套内部引擎。

## 5. 修改方向三：重做核心操作按钮

当前按钮更像开发者调试动作：

- Advance
- Complete Node
- Block Node
- Return to Node

建议改成用户语义：

- 继续执行
- 暂停任务
- 补充信息
- 重新处理上一步
- 标记完成
- 查看产出
- 保存结果

底层仍然可以调用原来的 workflow runner，但前台按钮必须换成用户目标，而不是状态机动作。

特别注意：

```text
Resume 不应该自动推进节点。
```

用户点击“继续任务”时，应该先回到现场，展示当前状态；只有用户再点击“继续执行”，才真正推进。

## 6. 修改方向四：把 Agent 真实执行补起来

目前工作流可以推进，但很多节点还只是状态流转或 placeholder 产物。用户会觉得“它没有真的干活”。

建议下一阶段选一个最小真实场景，例如：

```text
已有代码仓库迭代 Agent
```

让它跑通真实闭环：

1. 用户输入：“检查这个项目的工作台体验问题并提出修改方案”
2. 系统创建任务
3. Agent 分析项目
4. 生成问题清单
5. 生成修改计划
6. 必要时请求用户确认
7. 执行代码修改
8. 生成结果总结
9. 沉淀产物和记忆

只有这个闭环跑通，工作台才会从“流程板”变成“真助手”。

## 7. 修改方向五：模型配置改成向导

当前模型配置太工程化：Provider、Model、Binding、Secret 都直接暴露，普通用户配置成本高。

同时，模型配置不应继续作为强依赖工作区的配置项来设计。它更适合作为应用级公共能力：

```text
模型配置 = 全局公共模块
工作区 = 使用模型配置的业务容器
```

原因：

- 模型 Provider、API Key、默认模型通常属于用户本人或当前应用实例，而不是某一个工作区。
- 用户不应该每新建一个工作区就重新配置模型。
- 工作台、插件、结果沉淀、未来的多个 Agent 场景都应该复用同一套模型能力。
- 工作区可以有覆盖策略，但覆盖应该是高级能力，不应作为默认使用路径。

建议第一版改成三步：

1. 选择服务商：OpenAI / Anthropic / DeepSeek / MiMo / 自定义
2. 填 API Key 和 Base URL
3. 选择默认模型并测试连接

高级配置再折叠进去：

- 角色绑定模型
- 调用类型绑定
- 工作区覆盖（高级设置）
- 多 Provider 策略

这样第一次使用不会被配置页劝退。

### 7.1 模型配置的产品边界

建议将模型配置抽离为独立的应用级模块，不再要求用户先选择工作区才能配置模型。

推荐交互：

- 顶部导航保留“模型配置”。
- 用户可以从任何状态进入模型配置页。
- 没有工作区时，也可以完整配置模型。
- 配置完成后，所有工作区默认可用。
- 工作区级模型策略只作为高级设置出现，例如“此工作区使用单独模型”。

推荐配置层级：

| 层级 | 定位 | 默认是否展示 |
| --- | --- | --- |
| 应用级默认配置 | 所有工作区共用的 Provider、Model、Secret、默认模型 | 是 |
| 调用类型 / 角色绑定 | 不同任务角色或调用类型选择不同模型 | 折叠展示 |
| 工作区覆盖 | 特定工作区使用独立 provider/model/binding | 高级设置 |

推荐存储心智：

```text
全局模型配置：
  app model config

工作区模型覆盖：
  workspace model override
```

在前端体验上，模型配置页不应该出现“请先选择工作区，模型配置将关联到该工作区”这类提示。更合理的是：

```text
配置完成后，所有工作区都可以使用这套模型。你也可以在高级设置中为单个工作区单独覆盖。
```

### 7.2 模型配置交互原则：能选择就不要手写

模型配置页应尽量减少手动输入字段。凡是系统能通过内置 preset、下拉选项、单选、开关推导出来的配置，都不应该让用户手写。

当前需要修正的一个明确问题：

```text
服务商和模型目前都像是在填写配置表单，用户会觉得两者没有区别。
```

产品上必须把两者的交互职责拆开：

```text
服务商 = 配置连接
模型 = 选择能力
```

服务商阶段只解决“怎么连上某个平台”：

- 选择服务商
- 填 API Key
- 必要时修改 Base URL
- 测试连接

模型阶段只解决“默认用哪个模型干活”：

- 从该服务商的模型列表中选择
- 查看模型用途说明
- 设置默认模型

普通用户不应该在模型阶段手写：

- Model ID
- Model Name
- Capabilities
- Context Window

这些字段应由 provider preset 或远端模型列表自动生成。只有在“自定义模型 / 高级设置”中才允许手写。

推荐交互原则：

```text
服务商用选择
模型用选择
能力用勾选
调用类型用选择
认证方式用默认值
Base URL 自动填充
ID 自动生成
高级字段默认折叠
```

第一版模型配置向导建议改为：

1. 选择服务商。
2. 系统自动填充 Provider 名称、Base URL、认证方式和推荐模型。
3. 用户填写 API Key。
4. 用户从下拉列表选择默认模型。
5. 点击测试连接。
6. 连接通过后保存为应用级默认配置。

字段建议：

| 字段 | 推荐交互 | 说明 |
| --- | --- | --- |
| Provider | 下拉 / 卡片选择 | OpenAI、Anthropic、DeepSeek、MiMo、自定义 |
| Provider ID | 自动生成 | 例如 `deepseek`、`mimo`，不让普通用户手写 |
| Provider Name | 自动填充 | 可在高级设置里改 |
| API Base URL | 自动填充 | 高级设置允许修改 |
| Auth Header | 自动选择 | 例如 Bearer / api-key |
| API Key | 手写 | 密钥只能由用户输入 |
| Model | 下拉选择 | 根据 Provider preset 给出候选模型 |
| Model ID | 自动生成 | 不让普通用户手写 |
| Capabilities | 多选 / 自动识别 | chat、reasoning、tool_call、streaming 等 |
| Context Window | 预填 / 高级设置 | 不作为首屏必填 |
| Binding | 默认自动创建 | 高级设置再配置角色绑定 |

### 7.2.1 模型绑定区改为“使用场景模型配置”

本项只调整模型配置页中的 Binding 区域，不要求改动整个工作台 GUI 的命名。

当前问题：

```text
Binding / role / modelId / providerId / scope / priority
```

这些字段对开发有意义，但对用户不清晰。用户真正需要理解的是：

```text
不同使用场景分别用哪个模型？
```

因此，模型配置页中的“模型绑定 / Binding”建议改为：

```text
使用场景模型配置
```

推荐说明文案：

```text
所有场景默认使用默认模型。你可以为某些场景单独选择更合适的模型。
```

推荐使用场景采用方案 A：场景型命名。

| 使用场景 | 说明 | 默认行为 |
| --- | --- | --- |
| 需求理解 | 理解用户输入，判断任务类型 | 继承默认模型 |
| 任务规划 | 拆解任务步骤，决定执行路径 | 继承默认模型 |
| 任务执行 | 执行具体操作，生成产出 | 继承默认模型 |
| 结果检查 | 检查结果质量和风险 | 继承默认模型 |
| 总结归档 | 总结任务结果，沉淀成果与记忆 | 继承默认模型 |

修正：

| 不推荐 | 推荐 |
| --- | --- |
| 模型绑定 | 使用场景模型配置 |
| Binding | 使用场景 |
| role | 使用场景 |
| modelId | 使用模型 |
| providerId | 所属服务商（可弱化展示） |
| scope / priority | 高级设置 |

交互建议：

1. 默认展示一个表格或卡片列表。
2. 每一行是一个使用场景。
3. 用户只需要从下拉列表选择模型。
4. 未选择时显示“使用默认模型”。
5. 高级设置中保留底层 Binding 信息。
6. 系统自动生成和维护 `ModelBindingConfig`。

底层仍可继续使用 `ModelBindingConfig`，但普通用户界面不暴露 Binding 术语。

### 7.2.2 服务商与模型配置区职责拆分

当前需要修正的另一个明确问题：

```text
服务商配置和模型配置都像是在填写一组相似表单，用户分不清两者区别。
```

产品上需要把两者职责拆开：

```text
服务商 = 连接到哪里
模型 = 使用哪个能力
```

#### 服务商配置区

服务商配置区只负责“如何连上某个平台”。

用户需要理解的是：

```text
我使用哪家服务商？
我的 API Key 是什么？
接口地址是否正确？
```

普通用户只应看到：

| 字段 | 交互方式 | 说明 |
| --- | --- | --- |
| 服务商 | 卡片 / 下拉选择 | OpenAI、DeepSeek、MiMo、Anthropic、自定义 |
| API Key | 手写输入 | 唯一必须由用户填写的字段 |
| Base URL | 自动填充 | 默认隐藏或弱化，必要时可编辑 |
| 连接测试 | 按钮 | 显示状态、耗时、检查地址、失败原因 |

普通用户不应手写：

- Provider ID
- Provider Name
- Auth Header
- modelsPath
- chatCompletionsPath
- supportsStreaming

这些字段由 provider preset 自动生成，高级设置中可查看和修改。

#### 模型配置区

模型配置区只负责“在该服务商下使用哪个模型”。

用户需要理解的是：

```text
这个服务商下面，我默认用哪个模型？
这个模型更适合速度、质量、推理还是成本？
```

普通用户应看到的是模型选项，而不是模型表单：

| 字段 | 交互方式 | 说明 |
| --- | --- | --- |
| 模型 | 下拉 / 卡片选择 | 来自内置 preset 或远端模型列表 |
| 模型说明 | 只读展示 | 例如“速度快”“适合复杂推理”“成本低” |
| 默认模型 | 单选 / 设为默认 | 选择后自动保存 |
| 支持能力 | 标签展示 | reasoning、tool call、streaming 等 |

普通用户不应手写：

- Model ID
- Model Name
- Capabilities
- Context Window
- Provider ID

这些字段应由系统根据 preset 或远端模型列表自动生成。

只有在“自定义模型 / 高级设置”中，才允许手动填写模型字段。

#### 推荐交互流程

推荐把服务商和模型做成前后关系，而不是两个并列表单：

```text
选择服务商
  ↓
填写 API Key
  ↓
系统自动加载 / 生成该服务商的模型列表
  ↓
用户选择默认模型
  ↓
测试连接
  ↓
保存配置
```

对于 DeepSeek / MiMo / OpenAI 这类内置服务商：

- 用户不需要填写 Provider ID。
- 用户不需要填写 Model ID。
- 用户不需要填写模型名称。
- 用户只需要填 API Key，并选择一个推荐模型。

对于自定义服务商：

- 允许手写 Base URL 和模型名称。
- 但仍应提供示例、校验和高级提示。
- 不建议用裸 JSON 或完全自由表单作为默认入口。

#### 验收标准

服务商与模型配置区改造后，应满足：

- 用户能清楚理解服务商是“连接配置”，模型是“能力选择”。
- 配置 DeepSeek / MiMo 时，用户不需要手写模型 ID。
- 模型配置区不再像另一个服务商表单。
- 保存服务商后，系统能自动生成或展示推荐模型。
- 用户可以直接选择默认模型。
- 只有高级设置才暴露 Provider ID / Model ID / Auth Header / Context Window 等字段。

### 7.2.3 模型能力字段不应作为普通用户手写项

当前问题：

```text
模型配置里需要用户手写 capabilities，例如 chat, completion, reasoning。
```

这会造成几个问题：

- 用户不知道应该填什么。
- 填错会影响系统判断。
- 不同服务商的能力命名不统一。
- 普通用户会误以为这是必须理解的配置项。
- 模型配置区看起来更像数据库表单，而不是产品配置。

产品判断：

```text
任务编排和使用场景配置可以直接选择模型，因此能力不应成为普通配置主项。
```

能力字段的定位应改为：

```text
模型能力 = 系统元数据
```

它主要用于：

| 用途 | 说明 |
| --- | --- |
| 推荐 | 根据场景推荐更合适的模型 |
| 校验 | 防止把不支持文本生成、流式输出、视觉等能力的模型用于错误场景 |
| 功能开关 | 根据模型能力决定是否开启工具调用、流式输出、图片输入、结构化输出 |
| 自定义模型兜底 | 系统不知道自定义模型能力时，由高级用户声明 |

普通用户路径中不应出现能力手写字段。

推荐处理方式：

| 场景 | 能力来源 | 用户是否可编辑 |
| --- | --- | --- |
| 内置服务商推荐模型 | Provider preset 自动提供 | 否，只读展示 |
| 远端模型列表 | 系统拉取或映射能力 | 否，只读展示 |
| 使用场景模型配置 | 直接选择模型 | 否 |
| 自定义模型 | 用户在高级设置中勾选 | 是，但用复选框 |

普通模式下，模型卡片只展示中文能力标签：

- 普通对话
- 强推理
- 流式输出
- 工具调用
- 长上下文
- 视觉理解
- 结构化输出

高级 / 自定义模型中，如果确实需要调整能力，也应使用复选框：

```text
这个模型支持：
[ ] 普通对话
[ ] 强推理
[ ] 流式输出
[ ] 工具调用
[ ] 长上下文
[ ] 视觉理解
[ ] 结构化输出
```

不应让用户手写：

```text
chat,completion,reasoning
```

验收标准：

- 普通模型配置流程中不出现 capabilities 手写输入框。
- 内置模型能力由 preset 自动生成。
- 模型能力只作为标签展示。
- 使用场景配置直接选择模型，不要求配置能力。
- 自定义模型如需声明能力，使用中文复选框，不使用逗号分隔输入。

### 7.2.4 ID 字段不应作为普通用户输入项

当前问题：

```text
服务商、模型、模型绑定等配置中要求用户填写 id。
```

这对普通用户很不自然。用户关心的是：

```text
服务商叫什么？
模型是什么？
这个模型用在哪些场景？
```

用户不关心：

```text
provider-deepseek
model-deepseek-v4-pro
binding-task-planning-deepseek-v4-pro
```

让用户填写 ID 会带来问题：

- 用户不知道 ID 是什么。
- 不知道应该填中文还是英文。
- 容易重复。
- 容易包含非法字符。
- 保存失败时很难理解。
- 整体体验像数据库管理后台。

产品判断：

```text
ID 是系统内部字段，不应作为普通用户输入项。
```

推荐处理方式：

| ID 类型 | 生成方式 | 普通用户是否可见 |
| --- | --- | --- |
| Provider ID | 根据服务商 preset 或服务商名称自动生成 | 默认不可见 |
| Model ID | 根据 providerId + modelName 自动生成 | 默认不可见 |
| Binding ID | 根据使用场景 + modelId 自动生成 | 默认不可见 |
| Secret Key | 根据 providerId 自动生成 | 默认不可见 |

示例：

```text
用户选择 DeepSeek
→ providerId = deepseek

用户选择 DeepSeek V4 Pro
→ modelId = deepseek-v4-pro

用户设置“任务规划”使用 DeepSeek V4 Pro
→ bindingId = task-planning-deepseek-v4-pro
```

自定义服务商或自定义模型也应自动生成 ID。

例如：

```text
服务商名称：我的本地模型
→ providerId = custom-local-model

模型名称：llama-3-70b
→ modelId = custom-local-model-llama-3-70b
```

如果 ID 重复，系统自动追加后缀：

```text
custom-local-model-2
```

高级设置中可以展示 ID，用于排查、导出、调试，但默认不允许普通用户编辑。

验收标准：

- 配置 DeepSeek / MiMo / OpenAI 时不出现 ID 输入框。
- 添加模型时不要求用户填写模型 ID。
- 使用场景模型配置不要求填写 Binding ID。
- ID 重复由系统自动处理。
- ID 只在高级设置 / 调试信息中显示。
- 普通配置页面只展示名称、服务商、模型和使用场景。

### 7.2.5 模型配置 GUI 从“数据表管理”改为“模型连接与路由配置”

需要明确：模型配置页不是不能有设置，也不是只能做成小白向导。这个页面本来就会给开发者或高级用户使用。

真正的问题是：

```text
当前页面像在维护 Provider / Model / Binding / Secret 几张数据表，而不是在配置模型连接与使用策略。
```

开发者可以接受复杂配置，但仍需要：

- 结构清楚
- 字段有意义
- 顺序符合使用流程
- 错误可定位
- 修改可回退
- 默认值合理

当前页面容易让开发者困惑：

- 为什么服务商和模型都要手写 ID？
- 为什么模型能力要手写逗号字符串？
- 为什么 Binding 要自己造 ID？
- 为什么测试失败只有“连接失败”？
- 为什么保存后不好修改？
- 为什么 Provider / Model / Binding 三块像三张数据库表？
- 为什么默认模型、使用场景模型、API Key 之间的关系不清楚？

因此，模型配置页的改造目标应定义为：

```text
保留开发者可配置能力，但用更符合开发者心智的方式组织。
```

更准确的一句话：

```text
从“内部数据结构管理页”改成“开发者可理解的模型连接与路由配置页”。
```

#### 推荐页面结构

建议模型配置页按使用流程组织，而不是按数据对象组织：

```text
模型配置

当前默认配置
  - 服务商
  - 默认模型
  - 连接状态
  - 流式输出状态
  - 最近测试结果

服务商连接
  - 服务商类型
  - Base URL
  - API Key
  - 认证方式
  - 测试连接

可用模型
  - 从服务商同步 / 使用内置列表
  - 选择默认模型
  - 查看模型能力标签
  - 添加自定义模型

使用场景模型
  - 需求理解
  - 任务规划
  - 任务执行
  - 结果检查
  - 总结归档

高级设置
  - ID
  - Headers
  - Paths
  - Scope
  - Priority
  - 导入 / 导出
```

#### 推荐配置心智

开发者进入模型配置页时，应该按这个顺序理解：

1. 我先配置一个模型服务商。
2. 我验证它能连通。
3. 我选择或同步可用模型。
4. 我设一个默认模型。
5. 我按使用场景覆盖模型。
6. 我需要时进入高级参数。

不应要求开发者按下面这种数据库维护心智操作：

```text
先维护 Provider 表
再维护 Model 表
再维护 Binding 表
再处理 Secret 表
```

#### 字段展示规则

| 字段 / 概念 | 推荐处理 |
| --- | --- |
| ID | 自动生成，可在高级设置查看 |
| 能力 | 标签展示，高级设置中可勾选 |
| Binding | 前台改为“使用场景模型配置” |
| API Key | 可填写和修改，不展示 secret key 名称 |
| Base URL | 内置服务商自动填充，自定义服务商可编辑 |
| Auth Header | 内置服务商自动选择，高级设置可编辑 |
| Scope / Priority | 高级设置展示 |
| 测试错误 | 显示检查地址、耗时、状态码、响应摘要 |

#### 验收标准

- 页面默认不再像 Provider / Model / Binding 三张表。
- 开发者能按“连接服务商 → 选择模型 → 配置使用场景”的顺序完成配置。
- 默认模型和使用场景模型关系清晰。
- 服务商连接失败时能看到具体原因。
- 已保存配置可以再次编辑修改。
- ID、能力、scope、priority 等字段不作为主流程输入项。
- 高级设置保留完整可配置能力。

只有 `自定义 Provider` 才需要允许用户手写：

- Provider ID
- Provider Name
- Base URL
- Model Name
- Auth Header

但即使是自定义 Provider，也应提供表单校验和示例，而不是裸 JSON 编辑。

### 7.3 DeepSeek 模型接入要求

模型配置需要加入 DeepSeek 作为内置服务商选项。

参考文档：

```text
https://api-docs.deepseek.com/zh-cn/
```

DeepSeek API 兼容 OpenAI / Anthropic API 格式。第一阶段建议优先按 OpenAI API 兼容方式接入。

推荐内置 Provider Preset：

| 字段 | 建议值 |
| --- | --- |
| providerId | `deepseek` |
| providerName | `DeepSeek` |
| providerType | `openai-compatible` |
| defaultBaseUrl | `https://api.deepseek.com` |
| chatCompletionsPath | `/chat/completions` |
| authHeader | `Authorization: Bearer` |
| secretEnvName | `DEEPSEEK_API_KEY` |
| supportsStreaming | `true` |

推荐内置模型选项：

| 模型 | 用途 |
| --- | --- |
| `deepseek-v4-flash` | 默认快速模型 / 常规任务 |
| `deepseek-v4-pro` | 高质量推理 / 复杂任务 |

兼容保留项：

| 模型 | 说明 |
| --- | --- |
| `deepseek-chat` | 兼容旧配置，官方标记将于 2026-07-24 弃用 |
| `deepseek-reasoner` | 兼容旧配置，官方标记将于 2026-07-24 弃用 |

DeepSeek 配置向导中，用户选择 DeepSeek 后，应自动填充：

- Provider 名称：DeepSeek
- API Base URL：`https://api.deepseek.com`
- 认证方式：`Authorization: Bearer`
- API Key 字段提示：`DEEPSEEK_API_KEY`
- 模型下拉：`deepseek-v4-flash`、`deepseek-v4-pro`

用户不应手写模型名，除非打开“自定义模型”或“高级设置”。

DeepSeek 接入时需要注意：

- 默认以 OpenAI-compatible 协议实现。
- 请求路径为 `/chat/completions`。
- 需要支持 `stream: true`。
- 高级参数可以保留：
  - `thinking`
  - `reasoning_effort`
- `deepseek-chat` 和 `deepseek-reasoner` 仅作为旧配置兼容项，不作为新用户首选推荐。

### 7.4 MiMo 模型接入要求

模型配置需要加入 MiMo 作为内置服务商选项。

参考文档：

```text
https://platform.xiaomimimo.com/docs/zh-CN/quick-start/first-api-call
```

MiMo 开放平台兼容两种 API 格式：

- OpenAI API 格式
- Anthropic API 格式

第一阶段建议优先按 OpenAI API 兼容方式接入，降低适配复杂度。

推荐内置 Provider Preset：

| 字段 | 建议值 |
| --- | --- |
| providerId | `mimo` |
| providerName | `MiMo` |
| providerType | `openai-compatible` |
| defaultBaseUrl | `https://api.xiaomimimo.com/v1` |
| chatCompletionsPath | `/chat/completions` |
| defaultModel | `mimo-v2.5-pro` |
| authHeader | `api-key` 或 `Authorization: Bearer` |
| secretEnvName | `MIMO_API_KEY` |

配置向导中选择 MiMo 后，应自动填充：

- Provider 名称：MiMo
- API Base URL：`https://api.xiaomimimo.com/v1`
- 推荐模型：`mimo-v2.5-pro`
- API Key 字段提示：`MIMO_API_KEY`

用户只需要填入 API Key，然后点击“测试连接”。

MiMo 接入时需要注意：

- 默认以 OpenAI-compatible 协议实现。
- 后续可扩展 Anthropic-compatible 协议。
- API Key 必须进入应用级 secret store，不进入普通配置文件。
- 模型列表可以先用内置候选值，后续再支持从远端拉取。

### 7.5 流式输出要求

模型调用层必须支持流式输出，不能只支持一次性返回完整文本。

流式输出是 Agent 工作台的基础体验能力，原因：

- 用户能感知 Agent 正在工作，减少等待焦虑。
- 长任务可以持续写入“最近进展”。
- 后续工具调用、节点执行、结果生成都需要实时反馈。
- 可以把模型输出分段映射到任务过程记录、当前步骤说明和产物草稿。

模型调用接口建议同时支持两种模式：

```ts
type ModelInvokeMode = 'stream' | 'blocking'
```

默认策略：

| 场景 | 推荐模式 |
| --- | --- |
| 用户对话 / 任务理解 | stream |
| 长文本生成 / 总结 | stream |
| 节点执行过程说明 | stream |
| 健康检查 | blocking |
| 后台短分类 / 路由 | blocking |

模型调用层需要抽象统一事件：

```ts
type ModelStreamEvent =
  | { type: 'start'; requestId: string; modelId: string }
  | { type: 'delta'; text: string }
  | { type: 'reasoning_delta'; text: string }
  | { type: 'tool_call_delta'; toolCallId: string; name?: string; argumentsDelta?: string }
  | { type: 'done'; usage?: unknown }
  | { type: 'error'; message: string; recoverable: boolean }
```

前端消费流式输出时，不应直接暴露底层 chunk，而应映射到产品区域：

- 当前步骤说明
- 最近进展
- 产物草稿
- 需要用户确认的信息

MiMo 的 OpenAI-compatible 请求中需要支持 `stream: true`。如果某个模型或 provider 不支持流式输出，则模型配置状态中应明确标记：

```text
supportsStreaming: false
```

并在任务执行时自动降级到 blocking 模式。

## 8. 修改方向六：修正明确体验与逻辑问题

优先修这些问题：

- `Return to Node` 前端传的是 `targetNodeId`，后端需要 `toNodeId`，需要统一。
- `Resume` 不应直接 `advanceTaskWorkflow()`，应恢复现场。
- 工作区打开逻辑要保证目录不存在 manifest 时能创建。
- 模型配置和插件管理应抽离为应用级公共模块，不能依赖 active workspace 才能使用。
- 结果页可以依赖当前工作区，但不能只依赖内存里的 active workspace，最好能持久化最后工作区。
- 顶部产品文案要去掉“验收说明感”，改成真实用户语言。
- 中英文混用要收敛，至少主流程按钮统一中文。

## 9. 修改方向七：插件管理抽离为应用级能力库

插件管理也不应继续作为强依赖工作区的页面来设计。

更合理的产品边界是：

```text
插件管理 = 应用级能力库
工作区 = 使用 / 启用 / 覆盖插件能力的业务容器
```

原因：

- 插件本质上是 AgentThee 的能力扩展，例如 workflow、role、skill。
- 用户安装或管理插件时，通常是在管理“这个应用能做什么”，而不是“某个工作区文件夹里有什么”。
- 多个工作区应该可以复用同一批已安装插件。
- 工作区可以选择启用 / 禁用某些插件，但这应该是工作区策略，不是插件管理本身的前置条件。

### 9.1 插件管理的产品边界

建议将插件管理拆成两层：

| 层级 | 定位 | 页面位置 |
| --- | --- | --- |
| 应用级插件库 | 安装、删除、升级、查看插件详情、全局启停默认状态 | 插件管理 |
| 工作区插件策略 | 当前工作区启用哪些插件、是否覆盖默认配置 | 工作区设置 / 高级设置 |

插件管理页应该允许用户在没有工作区时进入，并完成以下动作：

- 查看已安装插件
- 添加插件
- 删除插件
- 查看插件类型、版本、能力说明
- 检查全局冲突
- 设置默认启用状态

不应出现：

```text
请先在工作台中选择一个工作区，插件管理将关联到该工作区。
```

更合理的提示是：

```text
插件会扩展 AgentThee 的全局能力。你可以在工作区设置中决定某个工作区是否启用它。
```

### 9.2 插件配置层级

推荐插件配置分层：

```text
应用级插件库：
  installed plugins
  default enablement
  global plugin config

工作区插件策略：
  workspace enablement override
  workspace plugin config override
```

解析顺序建议：

```text
工作区插件覆盖 → 应用级插件默认配置 → 内置默认能力
```

但默认用户界面只强调应用级插件库，不把工作区覆盖作为普通用户的主路径。

### 9.3 插件管理推荐交互

插件管理页主流程：

1. 用户进入插件管理。
2. 查看应用级已安装插件列表。
3. 添加插件或管理已有插件。
4. 系统做插件合法性和冲突检查。
5. 如果存在高风险影响，展示确认。
6. 确认后写入应用级插件库。
7. 用户可以选择是否设为“默认对所有工作区启用”。

工作区内使用插件的流程：

1. 用户进入某个工作区。
2. 打开工作区设置或高级设置。
3. 查看“此工作区启用的插件”。
4. 默认继承应用级插件配置。
5. 用户可对当前工作区做单独覆盖。

### 9.4 插件与模型的共同抽离原则

模型配置和插件管理都应从工作区主流程中抽离出来，作为应用级公共能力。

推荐心智：

```text
应用级能力：
  模型配置
  插件管理
  全局偏好设置

工作区级数据：
  任务
  会话
  产物
  Trace
  记忆
  结果沉淀
  工作区覆盖策略
```

这样可以避免每个工作区重复配置基础能力，也能让用户理解：

```text
我是在配置 AgentThee 的能力，而不是在配置某个任务文件夹。
```

## 10. 建议交互逻辑

本节描述改造后的核心交互路径。目标是让用户始终知道：

```text
我在哪里？
当前任务是什么状态？
系统下一步会做什么？
什么时候需要我介入？
结果沉淀在哪里？
```

### 10.1 应用启动后的总入口逻辑

应用启动后，默认进入“工作区首页”，而不是直接进入复杂工作台。

首页按状态展示不同主操作：

| 状态 | 用户看到的重点 | 主操作 |
| --- | --- | --- |
| 从未使用过 | 创建第一个工作区 | 打开 / 创建工作区 |
| 有最近工作区 | 最近工作区和最近任务 | 继续上次任务 |
| 有阻塞任务 | 哪些任务需要用户处理 | 查看阻塞 |
| 有进行中任务 | 当前正在推进什么 | 进入任务 |
| 无任务 | 可以开始一个新任务 | 新建任务 |

首页的第一屏不应只展示目录路径，而应展示“我能继续做什么”。

### 10.2 工作区打开与创建逻辑

用户点击“打开工作区”后：

1. 选择本地目录。
2. 系统检查目录下是否已有工作区 manifest。
3. 如果已有 manifest，直接打开并记录为最近工作区。
4. 如果没有 manifest，弹出确认：

```text
这个目录还不是 AgentThee 工作区，是否创建？
```

确认后：

1. 初始化工作区结构。
2. 写入 workspace manifest。
3. 加入最近工作区。
4. 进入工作台。

不应该出现“用户选择了目录，但进入工作台后没有任何可用状态”的情况。

### 10.3 模型配置状态与阻塞逻辑

进入工作台后，系统先检查应用级模型配置。

这里不能只用一句“模型未配置，无法启动任务”覆盖所有情况。

工作台应该把模型配置状态拆成可理解的用户状态：

| 状态 | 触发条件 | 工作台标题 | 主操作 |
| --- | --- | --- | --- |
| 未连接服务商 | 没有启用的 provider | 尚未连接模型服务商 | 连接服务商 |
| 服务商缺少密钥 | provider 存在但 API Key / secret 缺失 | 服务商缺少 API Key | 补充 API Key |
| 未选择模型 | provider 可用但没有 enabled model | 尚未选择可用模型 | 选择模型 |
| 未选择默认模型 | 有 enabled model，但没有 defaultModelId | 尚未选择默认模型 | 设置默认模型 |
| 未测试 | 有默认模型，但没有成功测试记录 | 模型尚未测试 | 测试模型 |
| 测试失败 | 最近一次服务商或模型调用测试失败 | 模型调用测试失败 | 查看失败原因 |
| 可用 | 服务商、API Key、默认模型和测试都可用 | 当前模型可用 | 配置 |

API Key 状态必须按真实 secret store 判断，而不是按“是否测试通过”判断。

正确判断：

```text
provider.apiKeyRef.key 指向的 secret 存在且非空
  → API Key 已填写
```

错误判断：

```text
没有连通性测试记录
  → 服务商缺少 API Key
```

如果 API Key 已保存但尚未测试，工作台应该显示：

```text
模型尚未测试
```

如果 API Key 已保存但测试失败，工作台应该显示：

```text
模型调用测试失败
```

而不是：

```text
服务商缺少 API Key
```

多服务商场景下，工作台只检查当前默认模型实际使用的服务商。非默认服务商缺 API Key，只能在该服务商卡片上做局部提示，不能阻塞整个工作台。

如果模型配置不可启动任务：

- 不展示复杂 workflow 面板作为第一重点。
- 展示明确阻塞说明，说明当前卡在哪一步。
- 给出一个主按钮，直接跳到对应配置位置。
- 可展示一个次按钮：“稍后配置，只浏览工作区”。

不同状态的推荐提示：

```text
尚未连接模型服务商。请先连接 DeepSeek、MiMo、OpenAI 或自定义服务商。
```

```text
尚未选择默认模型。已有可用模型，但系统不知道默认使用哪一个。
```

```text
模型调用测试失败。请查看失败原因并修正 API Key、Base URL、模型名或参数。
```

配置完成并测试通过后，自动返回上一个任务入口或工作台，并刷新工作台模型配置状态。

工作台刷新模型配置状态的时机：

- 首次进入工作台。
- 从模型配置页返回工作台。
- 切换工作区。
- 设置默认模型后。
- 完成服务商连通性测试后。
- 完成模型调用测试后。
- 用户点击“重新检查”后。

不允许只在“选择工作区”时刷新模型状态。否则用户已经完成模型配置后，工作台仍可能显示旧的“模型未配置”。

模型配置页本身不应要求先选择工作区。即使没有任何工作区，用户也应该能先完成模型配置。

如果未来支持工作区覆盖，则工作台检查模型时按以下顺序解析：

```text
工作区覆盖配置 → 应用级默认配置 → 未配置
```

但默认界面只强调应用级配置，避免用户误以为模型是工作区私有设置。

### 10.4 新任务启动逻辑

当工作区和模型都可用时，工作台第一重点应该是输入任务。

用户输入任务后，建议交互分两步：

1. 系统理解任务并生成任务草案。
2. 用户确认或调整后正式启动。

任务草案建议展示：

- 任务标题
- 任务类型
- 推荐流程
- 预计步骤
- 可能需要用户确认的点

用户可以选择：

- 开始执行
- 修改任务描述
- 更换任务类型
- 取消

这样可以避免用户输入一句话后系统直接进入一个用户无法理解的流程板。

### 10.5 任务执行中的主界面逻辑

任务执行中，主界面第一层只展示四块：

1. 当前任务
2. 当前进度
3. 下一步动作
4. 已有产出

推荐布局：

```text
顶部：当前任务标题 + 状态 + 主操作
左侧：任务列表 / 最近任务
中间：当前步骤和下一步
右侧：产出、需要确认、过程记录
```

主操作按钮按状态变化：

| 任务状态 | 主按钮 | 次按钮 |
| --- | --- | --- |
| ready | 开始执行 | 编辑任务 |
| running | 暂停 | 查看过程 |
| waiting_user | 提交补充信息 | 取消任务 |
| blocked | 处理阻塞 | 重新尝试 |
| reviewing | 确认结果 | 要求修改 |
| done | 查看结果 | 基于结果继续 |
| failed | 查看失败原因 | 重试 |

底层可以仍然使用 TaskRuntime 和 WorkflowNodeState，但用户不应该被迫理解这些字段。

### 10.6 继续任务与 Resume 逻辑

“继续任务”必须先恢复现场，而不是直接推进节点。

用户点击“继续任务”后：

1. 系统加载上次任务。
2. 展示任务当前状态。
3. 高亮当前步骤。
4. 展示上次停在哪里、为什么停下。
5. 如果有阻塞，展示阻塞原因和需要用户做什么。
6. 如果没有阻塞，展示“继续执行”按钮。

正确心智：

```text
继续任务 = 回到现场
继续执行 = 让 Agent 往下做
```

不要把这两个动作合并。

### 10.7 阻塞与用户确认逻辑

当任务进入阻塞或需要确认时，不应只显示 blocked badge。

需要展示：

- 阻塞原因
- 系统已经尝试了什么
- 需要用户提供什么
- 用户可以选择哪些处理方式

常见操作：

- 补充信息
- 允许继续
- 修改目标
- 跳过当前步骤
- 回到上一步
- 取消任务

对于高风险动作，使用确认弹窗，但弹窗必须说明：

- 要执行什么
- 为什么需要确认
- 可能影响什么文件 / 配置 / 产物
- 是否可以回退

### 10.8 产出与结果沉淀逻辑

任务执行中产生的内容先作为“产出”展示。

任务完成后，用户看到的是“结果页”或“任务总结”，而不是一堆 artifact ID。

完成态建议提供：

- 本次完成了什么
- 生成了哪些产出
- 还有哪些未完成
- 有哪些风险或技术债
- 建议下一步做什么
- 是否保存为可复用结果

结果沉淀建议由系统自动触发，但允许用户确认最终摘要：

1. 系统生成总结。
2. 用户查看并可编辑。
3. 用户点击“保存结果”。
4. 系统写入结果仓库和记忆系统。

### 10.9 历史任务与复用逻辑

用户从结果页或历史任务进入时，系统不应要求用户手动输入 taskId。

推荐交互：

- 点击历史任务。
- 查看任务结果。
- 点击“基于此结果继续”。
- 系统生成新的任务草案。
- 草案自动引用历史产出和上下文。
- 用户确认后启动新任务。

taskId、artifactId、traceId 可以保留在高级信息里，但不应成为普通用户的主操作输入。

### 10.10 高级详情与调试模式

Run、Node、Trace、Runtime、ArtifactIndex 仍然有价值，但建议放进“高级详情”或“调试模式”。

入口可以是：

```text
查看技术详情
```

高级详情里展示：

- TaskRuntime
- Workflow context
- Node state
- Trace events
- Artifact index
- Memory manifest
- IPC / storage 错误

这样既保留工程可观察性，又不干扰普通使用路径。

### 10.11 推荐主流程状态图

```text
启动应用
  ↓
工作区首页
  ↓
选择 / 创建工作区
  ↓
检查模型配置
  ├─ 未配置 → 模型配置向导 → 返回工作台
  └─ 已配置
       ↓
输入任务
  ↓
生成任务草案
  ↓
用户确认启动
  ↓
任务执行中
  ├─ 需要用户 → 补充信息 / 确认 / 修改目标
  ├─ 阻塞 → 处理阻塞 / 重试 / 回流
  ├─ 失败 → 查看原因 / 重试
  └─ 完成
       ↓
结果总结
  ↓
保存结果
  ↓
基于结果继续 / 返回首页
```

## 11. 建议改造优先级

### 第一阶段：先修“能不能顺畅用”

1. 工作区入口闭环
2. 模型配置抽离为应用级公共模块，并提供向导
3. 插件管理抽离为应用级能力库
4. 工作台空态和继续入口
5. Resume 行为修正
6. Return to Node bug 修复

### 第二阶段：修“像不像产品”

1. 主界面信息降噪
2. 按钮语义重写
3. Trace / Runtime 降级到高级详情
4. 文案统一
5. 视觉密度降低

### 第三阶段：修“是不是真 Agent”

1. 选定第一个真实任务场景
2. 接入模型调用
3. 节点真实执行
4. 产物真实生成
5. 结果沉淀和复用闭环

## 12. 一句话修改方向

不要继续把内部能力堆到界面上，而是先加一层产品抽象：

```text
用户看到的是任务、进展、阻塞和结果；系统内部才是 Run、Node、Trace 和 Artifact。
```
