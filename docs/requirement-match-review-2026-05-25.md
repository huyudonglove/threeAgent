## 4. 部分匹配项与问题记录

以下问题建议视为当前最重要的同步项。

### 4.1 模型配置能力只完成了基础版，未完全对齐需求文档

判定：**部分匹配**

需求文档明确要求了以下能力：

- 默认 provider
- 默认模型
- 按角色绑定模型
- 按调用类型绑定模型
- 全局配置与工作区覆盖配置区分
- 首页或 Run 总览阻塞提示并支持直达配置页

当前项目实际情况：

- 已支持 Provider / Model / Binding 基础管理
- 已支持按角色的 Binding 基础录入
- 未看到明确的“默认 provider”设置入口
- 未看到明确的“默认模型”设置入口
- 未看到“按调用类型绑定模型”的界面与数据处理
- 未看到“全局配置 / 工作区覆盖”在 UI 中被清晰区分
- 工作台页面未看到“模型未配置时的明显阻塞提示 + 直接跳转配置页”

影响：

- 基础可用，但离需求文档中的“可解释、可切换、可覆盖”的模型配置能力还有差距
- 技术经理若按需求文档理解当前完成度，容易高估该模块收敛度

### 4.2 模型配置管理器目前只显式管理全局配置，工作区覆盖能力未真正落地

判定：**部分匹配**

`src-main/model-config/contracts.ts` 中已存在：

- `GlobalModelConfig`
- `WorkspaceModelConfig`

但 `src-main/model-config/model-config-manager.ts` 当前主要读写的是：

- `global-config.json`

未见对应的工作区覆盖配置读写主流程，也未见“全局 -> 工作区覆盖 -> 最终解析”在管理器层被完整展开。

影响：

- 数据契约层已经表达了“全局 / 工作区”两层配置
- 实际管理器与 UI 仍主要按单层全局配置运行
- 这会让“需求文档已要求多层配置来源”与“当前实现只有单层主路径”之间形成落差

### 4.3 README 与当前实现严重不同步

判定：**不匹配**

`README.md` 仍在描述以下旧状态：

- `src/data/workbench.ts` 主要提供 Mock 数据
- preload 暴露的是较原始的 IPC 用法
- “后续规划”仍写着把 Mock 数据替换成真实运行时数据

但当前项目实际上已经有：

- `window.agentAPI` 窄接口
- `src-main/*` 大量主进程业务模块
- `useWorkbenchData` 与真实 IPC 数据模式
- 独立模型配置页
- 集成测试与恢复测试

影响：

- 新接手的人会被 README 误导
- 项目看起来像“早期壳子”，但实际已进入主干实现阶段
- 项目文档与代码状态不一致，会直接影响技术判断

### 4.4 开发计划文档中的完成描述高于当前需求匹配完成度

判定：**部分匹配**

`docs/development-plan.md` 中对 T15 / M3 的完成描述偏乐观，例如会让读者理解为模型配置页已经完整满足需求文档。

但从当前代码与需求文档对照来看，T15 更接近：

- 已完成基础模型配置能力
- 尚未完整覆盖默认模型、调用类型绑定、工作区覆盖、首页阻塞跳转等需求点

影响：

- 项目文档若直接作为状态依据，容易让后续开发跳过仍需收敛的点

建议：

- 保留“基础能力已完成”的判断
- 同时在计划文档或后续检查记录中注明“需求级完整对齐仍有缺口”
