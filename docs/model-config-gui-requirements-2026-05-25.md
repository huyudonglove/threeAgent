# 模型配置 GUI 改造需求文档（2026-05-25）

## 1. 背景

当前模型配置页已经开始从“数据表管理”转向“模型连接与路由配置”，页面里也已经出现了服务商连接、可用模型、默认调用参数、使用场景、高级设置等模块。

但从实际页面复查来看，当前版本仍然不能交给开发直接按现状延续。主要问题不是功能少，而是字段层级和交互路径仍然混乱：

```text
默认配置路径里仍在暴露内部字段；
服务商、模型、调用参数、使用场景的边界还不够清楚；
连接失败和模型调用失败没有被拆开表达。
```

必须修正后，开发者才能一眼看懂：

```text
我连的是哪家服务商，用的是哪个模型，默认怎么调用，不同使用场景是否有覆盖。
```

## 2. 当前页面复查结论

### 2.1 已经接近正确的地方

- 页面标题和主方向已经改为“模型连接与路由配置”。
- 已有内置服务商入口：OpenAI、Anthropic、DeepSeek、MiMo、自定义。
- 已有“当前配置摘要”。
- 已有“服务商连接”。
- 已有“可用模型”。
- 已有“默认调用参数”，包含 `temperature`、`top_p`、`max_tokens`、`stream`、`timeout_ms`、`retry_count`、`reasoning_effort`、`response_format`、`tool_calling`。
- 已有“使用场景”雏形。
- 已有高级设置折叠区。

### 2.2 仍然必须修改的地方

| 问题 | 当前表现 | 修改要求 |
| --- | --- | --- |
| 首配向导仍像内部表单 | 第 3 步无模型时要求添加模型，并填写模型 ID、模型名称、显示名称、能力、上下文窗口 | 内置服务商必须自动出现推荐模型；默认路径禁止填写 ID、能力、上下文窗口 |
| 服务商 ID 暴露 | 自定义服务商配置里仍可能要求填写服务商 ID | ID 由系统生成；只在高级设置展示 |
| 模型能力仍像用户输入项 | 向导或编辑表单里仍让用户理解能力字段 | 能力是系统元数据；默认视图只读展示，只有高级自定义模型可勾选 |
| 服务商测试和模型调用测试混在一起 | 连接测试只表达“连接失败”，用户不知道是 API Key、Base URL 还是模型名问题 | 拆成“服务商连通性测试”和“模型调用测试” |
| 使用场景命名不统一 | 当前页面仍出现任务编排、需求分析、技术方案、代码开发、项目管理等工程角色 | 配置页统一为：需求理解、任务规划、任务执行、结果检查、总结归档 |
| 仍出现“AI 角色”类描述 | 容易让用户以为改了工作流角色或 GUI 全局概念 | 此处只表达“使用场景的模型配置”，不改底层流程，不改主 GUI 名称 |
| 高级设置边界不清 | 高级字段虽然折叠，但仍穿插在主配置表单里 | 高级字段应集中到高级设置，不影响默认配置流程 |

## 3. 改造目标

将模型配置页从：

```text
Provider / Model / Binding 三张内部表的编辑器
```

改成：

```text
服务商连接 + 模型选择 + 调用参数 + 使用场景路由
```

目标不是减少开发者可配置项，而是把配置项放到正确位置：

1. 默认路径只放高频、必要、可理解字段。
2. 高级设置保留完整调试能力。
3. 内置服务商和内置模型尽量选择，不让用户手写。
4. 失败原因必须能指导用户下一步修改。

## 4. 范围

本需求只改造模型配置页。

包括：

- 首次配置向导
- 服务商连接配置
- 可用模型选择
- 默认模型配置
- 默认调用参数
- 使用场景模型与参数覆盖
- 高级设置
- 连接测试、模型调用测试、错误展示

不包括：

- 工作台主界面改名
- workflow / node / runtime 底层流程重构
- 插件管理页改造
- Agent 执行链路重新设计

## 5. 页面信息架构

模型配置页按以下结构组织：

```text
模型配置

1. 当前配置摘要
2. 服务商连接
3. 可用模型
4. 默认调用参数
5. 使用场景模型与参数
6. 高级设置
```

### 5.1 当前配置摘要

展示系统当前实际会使用的配置。

| 字段 | 说明 |
| --- | --- |
| 默认服务商 | 当前默认 provider |
| 默认模型 | 当前默认 model |
| 服务商连通性 | 最近一次服务商连接测试结果 |
| 模型调用状态 | 最近一次模型调用测试结果 |
| 流式输出 | 当前默认模型是否支持并启用 streaming |
| 默认调用参数 | 摘要展示 temperature / top_p / max_tokens / stream |
| 最近测试时间 | 最后一次测试时间 |

操作：

- 测试服务商连接
- 测试模型调用
- 修改默认模型
- 修改默认调用参数

## 6. 首次配置向导

首配向导是当前页面最需要修正的地方。

### 6.1 推荐流程

```text
选择服务商
  ↓
填写 API Key，确认 Base URL
  ↓
系统展示推荐模型
  ↓
选择默认模型
  ↓
测试服务商连接
  ↓
测试模型调用
  ↓
保存并完成
```

### 6.2 向导默认路径只能出现这些字段

| 步骤 | 可见字段 |
| --- | --- |
| 选择服务商 | OpenAI、DeepSeek、MiMo、Anthropic、自定义 |
| 配置连接 | API Key、Base URL |
| 选择模型 | 推荐模型列表、默认模型选择 |
| 测试 | 服务商连通性测试、模型调用测试、错误详情 |

### 6.3 向导默认路径禁止出现这些字段

- Provider ID
- Model ID
- Binding ID
- Model Name 手写输入
- Capabilities 手写输入
- Context Window 手写输入
- Scope
- Priority
- Auth Header
- API Path
- Secret Key 名称

这些字段只能出现在高级设置。

### 6.4 无模型时的处理

选择内置服务商后，即使远端模型列表不可用，也必须先显示内置推荐模型。

禁止出现这种首配体验：

```text
没有模型 → 请手动添加模型 → 填写模型 ID / 模型名称 / 能力
```

正确体验：

```text
没有远端模型列表 → 使用内置推荐模型 → 可选“同步远端模型列表” → 高级设置里可添加自定义模型
```

## 7. 服务商连接

### 7.1 定义

服务商负责回答：

```text
模型接口从哪里连？
```

服务商只负责连接信息，不负责具体模型能力选择。

### 7.2 默认视图字段

| 字段 | 交互方式 | 说明 |
| --- | --- | --- |
| 服务商 | 卡片 / 下拉选择 | OpenAI、DeepSeek、MiMo、Anthropic、自定义 |
| API Key | 密码输入 | 默认视图中唯一必须手动填写的连接凭证 |
| Base URL | 自动填充，可编辑 | 内置服务商默认填好 |
| 服务商连通性测试 | 按钮 | 检查 Base URL、API Key、认证方式 |

### 7.3 默认视图不展示

- Provider ID
- Auth Header
- modelsPath
- chatCompletionsPath
- supportsStreaming
- Secret Key 名称

### 7.4 内置服务商

| 服务商 | Base URL | 协议 |
| --- | --- | --- |
| OpenAI | `https://api.openai.com/v1` | OpenAI-compatible |
| DeepSeek | `https://api.deepseek.com` | OpenAI-compatible |
| MiMo | `https://api.xiaomimimo.com/v1` | OpenAI-compatible |
| Anthropic | `https://api.anthropic.com` | Anthropic-compatible |
| 自定义 | 用户填写 | OpenAI-compatible 优先，可高级配置 |

### 7.5 DeepSeek / MiMo 要求

- DeepSeek 必须作为内置服务商，不让用户手写 provider 配置。
- MiMo 必须作为内置服务商，不让用户手写 provider 配置。
- DeepSeek 和 MiMo 默认按 OpenAI-compatible 协议处理。
- 两者都必须支持流式输出开关。

## 8. 可用模型

### 8.1 定义

模型负责回答：

```text
这个服务商下面具体用哪个模型？
```

模型不应该表现为另一张手写表单。

### 8.2 模型来源优先级

内置服务商选择后，模型列表按以下逻辑生成：

1. 先展示内置推荐模型。
2. 用户可点击“同步远端模型列表”。
3. 远端列表成功后，合并或更新可用模型。
4. 远端列表失败时，不影响内置推荐模型使用。
5. 自定义模型只在高级设置里添加。

### 8.3 模型卡片字段

| 字段 | 说明 |
| --- | --- |
| 显示名称 | 例如 DeepSeek Chat、MiMo 7B |
| API 模型名 | 弱化展示，例如 `deepseek-chat` |
| 用途说明 | 例如“适合通用任务”“适合推理任务” |
| 能力标签 | 只读标签，例如“强推理”“流式输出”“工具调用” |
| 上下文长度 | 只读展示，可弱化 |
| 是否默认 | 当前是否为默认模型 |

### 8.4 默认视图不展示输入

默认视图不允许用户填写：

- Model ID
- Model Name
- Capabilities
- Context Window
- Provider ID

### 8.5 自定义模型

自定义模型只放在高级设置。

高级自定义模型可以配置：

- API 模型名
- 显示名称
- 上下文窗口
- 能力标签
- 是否启用

其中 ID 仍由系统自动生成。

## 9. 默认调用参数

### 9.1 定义

默认调用参数负责回答：

```text
没有项目覆盖时，系统默认怎样调用模型？
```

这部分是开发者需要明确看到的配置，不能缺失。但它不应被设计成全局唯一参数。

模型调用参数必须支持分层：

```text
应用级模型默认参数
  ↓
项目级模型参数覆盖
  ↓
项目级使用场景参数覆盖
```

原因：

- 不同模型适合不同参数，例如推理模型和通用对话模型的 `temperature`、`max_tokens`、`reasoning_effort` 不应完全相同。
- 不同项目对稳定性、创造性、输出长度、成本和响应速度的要求不同。
- 项目配置需要可迁移，不能依赖用户在另一个环境里手动记住一堆参数。

### 9.2 必须支持的参数

| 参数 | 说明 | 推荐交互 |
| --- | --- | --- |
| `temperature` | 控制随机性，越低越稳定 | 滑块 + 数字输入 |
| `top_p` | 控制采样范围 | 滑块 + 数字输入 |
| `max_tokens` | 最大输出长度 | 预设下拉 + 自定义数字输入 |
| `stream` | 是否流式输出 | 开关 |
| `timeout_ms` | 请求超时时间 | 数字输入 |
| `retry_count` | 失败重试次数 | 数字输入 |
| `reasoning_effort` | 推理强度 | 下拉选择 |
| `response_format` | 输出格式 / JSON 模式 | 下拉选择 |
| `tool_calling` | 是否允许工具调用 | 开关 |

### 9.3 参数配置层级

| 层级 | 配置内容 | 存储位置 | 是否可迁移 |
| --- | --- | --- | --- |
| 应用级服务商连接 | API Key、Base URL、认证方式 | 应用配置 / secrets | 不随项目迁移 |
| 应用级模型默认参数 | 某个模型的默认 temperature、top_p、max_tokens、stream 等 | 应用模型配置 | 可作为本机默认值 |
| 项目级模型参数 | 当前项目对某个模型的参数覆盖 | 项目配置 | 随项目迁移 |
| 项目级使用场景参数 | 需求理解 / 任务规划等场景的模型和参数覆盖 | 项目配置 | 随项目迁移 |

### 9.4 展示方式

- 默认调用参数作为独立模块保留。
- 可以提供“稳定 / 均衡 / 创造 / 自定义”预设，但必须允许开发者看到并修改具体参数。
- 参数修改后必须持久化，不能只停留在前端状态。
- 当前模型不支持的参数要禁用，并说明原因。
- 不同服务商参数名不一致时，前端展示统一字段，由后端适配。

### 9.5 默认值建议

| 参数 | 默认值 |
| --- | --- |
| `temperature` | `0.7` |
| `top_p` | `1` |
| `max_tokens` | 根据模型自动推荐 |
| `stream` | 开启，如果模型支持 |
| `timeout_ms` | `30000` |
| `retry_count` | `1` |
| `reasoning_effort` | `auto` |
| `response_format` | `text` |
| `tool_calling` | 根据模型能力默认关闭或自动 |

### 9.6 `max_tokens` 交互规则

`max_tokens` 不允许做成无约束的自由输入框。

推荐交互：

```text
预设下拉为主，自定义输入为辅
```

下拉选项按当前模型动态生成：

| 选项 | 含义 | 示例值 |
| --- | --- | --- |
| 短输出 | 简短回答、摘要、小段文本 | `1024` |
| 常规输出 | 默认推荐值，适合多数任务 | `4096` |
| 长输出 | 长文档、复杂任务、代码生成 | `8192` |
| 最大可用 | 当前模型允许的最大输出上限 | 根据模型动态计算 |
| 自定义 | 开发者手动输入具体值 | 受校验限制 |

生成规则：

- 每个模型 preset 应提供推荐 `max_tokens` 和最大输出上限。
- 如果服务商只提供上下文窗口，系统需要预留输入 token 空间，不能直接把 `context_window` 当作最大输出上限。
- 预设值不能超过当前模型最大输出上限。
- 如果模型最大输出上限低于某个预设值，该预设应隐藏或禁用，并说明原因。

自定义输入规则：

- 只能输入正整数。
- 必须大于 `0`。
- 必须小于或等于当前模型最大输出上限。
- 建议提供步进器，步长可为 `256` 或 `512`。
- 超出范围时不能保存，并提示当前模型允许范围。

提示文案示例：

```text
推荐：4096；当前模型最高：8192。
```

```text
该模型最高支持 4096 输出 token，请降低 max_tokens。
```

项目级覆盖和使用场景覆盖中的 `max_tokens` 也必须使用同一套规则，不能绕过校验。

## 10. 每个模型的高级参数配置

### 10.1 定义

每个模型都应该拥有自己的高级调用参数，而不是所有模型共用一套参数。

模型参数负责回答：

```text
这个模型默认应该怎么调用？
```

这里的“高级参数”不是全局参数，也不是只在系统默认配置里设置一次。它必须绑定到具体模型。

例如：

| 模型类型 | 参数倾向 |
| --- | --- |
| 通用对话模型 | `temperature` 可以较高，输出更自然 |
| 推理模型 | `temperature` 较低，`reasoning_effort` 更重要 |
| 结构化输出模型 | `response_format` 更重要，随机性应更低 |
| 长上下文模型 | `max_tokens`、上下文限制和超时更重要 |

### 10.2 每个模型必须可单独配置的高级参数

每个模型至少支持以下独立配置：

| 参数 | 说明 |
| --- | --- |
| `temperature` | 随机性 |
| `top_p` | 采样范围 |
| `max_tokens` | 最大输出长度，使用预设下拉 + 自定义输入，并受模型上限校验 |
| `stream` | 是否启用流式输出 |
| `timeout_ms` | 请求超时时间 |
| `retry_count` | 失败重试次数 |
| `reasoning_effort` | 推理强度 |
| `response_format` | 输出格式 / JSON 模式 |
| `tool_calling` | 是否允许工具调用 |

可选扩展参数：

| 参数 | 说明 |
| --- | --- |
| `frequency_penalty` | 降低重复表达 |
| `presence_penalty` | 提高新主题出现概率 |
| `stop` | 停止词 |
| `seed` | 固定随机种子 |
| `parallel_tool_calls` | 是否允许并行工具调用 |

不同服务商不支持的参数可以禁用，但不能让所有模型只能共用一套高级参数。

### 10.3 默认视图交互

在“可用模型”中选择某个模型后，应能进入该模型的参数配置。

每个模型至少支持：

- 使用系统推荐参数
- 使用应用级自定义参数
- 在当前项目中覆盖参数
- 恢复默认参数

推荐交互：

```text
模型卡片 / 模型详情
  ↓
高级参数
  ↓
应用级参数 / 当前项目覆盖
```

开发者应能清楚看到当前编辑的是：

```text
DeepSeek Chat 这个模型的高级参数
```

而不是：

```text
全局高级参数
```

### 10.4 参数继承逻辑

```text
模型 preset 推荐参数
  ↓
应用级该模型参数
  ↓
项目级该模型参数
  ↓
项目级使用场景参数
```

优先级越往下越高。

### 10.5 项目级覆盖

项目级模型参数必须允许单独配置。

同一个模型在不同项目中可以有不同参数：

| 项目 | 模型 | 参数策略 |
| --- | --- | --- |
| 项目 A：写作助手 | DeepSeek Chat | 较高 temperature，较长输出 |
| 项目 B：代码审查 | DeepSeek Chat | 较低 temperature，严格结构化输出 |
| 项目 C：任务执行 | MiMo | 开启 stream，较短输出，较快超时 |

### 10.6 可移植性要求

项目配置导出时，应包含：

- 项目默认模型引用
- 项目级模型参数覆盖
- 使用场景模型选择
- 使用场景参数覆盖

项目配置导出时，不应包含：

- API Key
- 本机 secret 路径
- 本机绝对路径
- 只能在当前机器生效的隐藏 ID

导入项目配置时，如果本机没有对应服务商或模型，应提示用户映射：

```text
项目需要 DeepSeek / deepseek-chat
本机未配置 DeepSeek API Key
请先连接服务商，或选择另一个可用模型替代。
```

## 11. 使用场景模型与参数

### 11.1 命名

配置页中使用：

```text
使用场景模型配置
```

不要在默认视图中出现：

- Binding
- 绑定
- role
- AI 角色

这里不是改工作流，也不是改 GUI 全局概念，只是让用户理解不同使用场景可以选择不同模型和参数。

### 11.2 固定使用场景

采用以下 5 个场景：

| 使用场景 | 说明 |
| --- | --- |
| 需求理解 | 理解用户输入，判断任务类型 |
| 任务规划 | 拆解任务步骤，决定执行路径 |
| 任务执行 | 执行具体操作，生成产出 |
| 结果检查 | 检查结果质量和风险 |
| 总结归档 | 总结任务结果，沉淀成果与记忆 |

### 11.3 默认视图交互

每个使用场景一行：

| 使用场景 | 当前模型 | 参数策略 | 操作 |
| --- | --- | --- | --- |
| 需求理解 | 使用默认模型 | 使用默认参数 | 更换模型 / 覆盖参数 |
| 任务规划 | DeepSeek Reasoner | 自定义参数 | 更换模型 / 覆盖参数 |

### 11.4 覆盖逻辑

默认逻辑：

```text
使用场景未配置 → 使用项目默认模型 + 该模型在项目中的参数
```

可单独覆盖：

- 模型
- `temperature`
- `top_p`
- `max_tokens`
- `stream`
- `timeout_ms`
- `reasoning_effort`
- `response_format`
- `tool_calling`

### 11.5 默认视图不展示

- bindingId
- role
- providerId
- scope
- priority

这些字段由系统自动维护，放到高级设置。

## 12. 模型能力字段

### 12.1 定位

模型能力不是默认配置路径里的用户输入项。

能力字段定位为：

```text
系统元数据
```

用途：

- 展示模型特点
- 推荐模型
- 判断模型是否支持流式输出、工具调用、结构化输出等能力
- 在使用场景中提示模型是否合适
- 自定义模型兜底

### 12.2 展示方式

默认视图只展示中文标签：

- 普通对话
- 强推理
- 流式输出
- 工具调用
- 长上下文
- 视觉理解
- 结构化输出

### 12.3 编辑方式

内置模型：

```text
能力只读，由 preset 或远端模型列表提供。
```

自定义模型：

```text
能力可在高级设置中用复选框勾选。
```

禁止使用逗号字符串输入：

```text
chat,completion,reasoning
```

## 13. ID 字段

### 13.1 定位

ID 是系统内部字段，不应作为默认路径里的输入项。

### 13.2 自动生成规则

| ID 类型 | 生成方式 |
| --- | --- |
| Provider ID | 根据服务商 preset 或名称自动生成 |
| Model ID | 根据 providerId + modelName 自动生成 |

- 默认视图不展示 ID 输入框。
- 高级设置可以展示 ID。
- 默认不可编辑。
- ID 冲突由系统自动追加后缀解决。

## 14. 测试与错误处理

### 14.1 测试必须拆成两类

| 测试 | 目的 | 常见失败原因 |
| --- | --- | --- |
| 服务商连通性测试 | 验证 Base URL、API Key、认证方式是否可用 | API Key 缺失、Base URL 错误、认证头错误、网络失败 |
| 模型调用测试 | 验证选中的模型名、参数、流式输出是否可调用 | 模型名不存在、模型无权限、参数不支持、stream 不支持 |

### 14.2 服务商连通性测试

展示：

- 状态
- 耗时
- 检查地址
- HTTP 状态码
- 响应摘要
- API Key 是否缺失
- Base URL 是否可能错误
- 认证方式是否可能不匹配

### 14.3 模型调用测试

使用当前选中的默认模型发起一次最小请求。

测试内容：

- 非流式普通输出是否成功
- 如果启用 `stream`，流式输出是否成功
- 当前默认参数是否被服务商接受

展示：

- 模型名
- 请求模式：stream / non-stream
- 耗时
- HTTP 状态码
- 响应摘要
- 失败原因

### 14.4 保存失败必须支持恢复

保存失败时：

- 保留用户已填写内容。
- 展示具体失败原因。
- 允许返回修改。
- 允许再次测试。
- 已保存配置必须可再次编辑。

禁止只显示：

```text
连接失败
模型保存失败
```

## 15. 模型配置状态定义

工作台和模型配置页不能只用一个 `hasProvider && hasModel` 判断所有情况。

配置状态必须拆成更细的状态，让用户知道下一步应该改什么。

### 15.1 状态枚举

| 状态 | 判断条件 | 用户含义 | 是否允许启动任务 |
| --- | --- | --- | --- |
| `no_provider` | 没有启用的服务商 | 还没有连接任何模型服务商 | 否 |
| `provider_missing_key` | 有服务商，但 API Key 缺失或 secret 不存在 | 服务商已创建，但不能认证 | 否 |
| `no_model` | 有启用服务商，但没有可用模型 | 还没有选择或添加模型 | 否 |
| `no_default_model` | 有可用模型，但没有设置默认模型 | 系统不知道默认用哪个模型 | 否 |
| `not_tested` | 有默认模型，但没有成功测试记录 | 配置看起来完整，但尚未验证可用 | 可允许启动，但强提示测试 |
| `test_failed` | 最近一次服务商或模型调用测试失败 | 配置不可用或不稳定 | 不建议启动；可允许重试 |
| `ready` | 有启用服务商、API Key、可用模型、默认模型，且最近测试成功 | 模型配置可用 | 是 |

### 15.2 判断顺序

按以下顺序计算状态，命中后立即返回：

```text
没有启用 provider
  → no_provider

provider 缺少 API Key / secret
  → provider_missing_key

没有启用 model
  → no_model

没有 defaultModelId，或 defaultModelId 指向的模型不存在 / 被禁用
  → no_default_model

没有测试记录
  → not_tested

最近测试失败
  → test_failed

最近测试成功
  → ready
```

### 15.2.1 API Key 状态判断规则

`provider_missing_key` 只能表示：

```text
API Key 没有保存，或 provider.apiKeyRef 指向的 secret 不存在 / 为空。
```

不能把下面这些情况归类为 `provider_missing_key`：

- API Key 已保存，但连通性测试还没做。
- API Key 已保存，但 Base URL 错误。
- API Key 已保存，但模型名错误。
- API Key 已保存，但服务商返回 401 / 403。
- API Key 已保存，但网络失败。
- API Key 已保存，但服务商接口超时。

这些情况应该归到：

```text
not_tested
test_failed
```

或者在错误详情里展示为：

```text
认证失败 / Base URL 错误 / 模型名无效 / 网络失败
```

判断 API Key 是否存在时，必须读取真实 secret store：

```text
provider.apiKeyRef.key
  ↓
secrets[provider.apiKeyRef.key]
  ↓
存在且非空 → API Key 已填写
不存在或为空 → provider_missing_key
```

不能使用以下方式判断 API Key 是否存在：

```text
是否连通过测试
是否在本次页面会话里测试成功
是否存在前端临时 providersWithKey 集合
```

### 15.2.2 多服务商时的判断范围

默认工作台状态只检查“当前会被使用的服务商”。

判断顺序：

```text
默认模型 → 该模型所属 provider → 检查该 provider 的 API Key
```

如果还没有默认模型：

```text
默认服务商 → 检查默认服务商 API Key
```

不要因为某个非默认服务商缺 API Key，就阻塞整个工作台。

例如：

```text
DeepSeek 是默认模型服务商，并且 API Key 存在
MiMo 没有 API Key
```

工作台不应显示：

```text
服务商缺少 API Key
```

只应在 MiMo 服务商卡片上显示局部提示：

```text
MiMo 缺少 API Key
```

### 15.3 状态接口返回字段

模型配置状态接口建议返回：

| 字段 | 说明 |
| --- | --- |
| `state` | 状态枚举 |
| `canStartTask` | 是否允许启动任务 |
| `severity` | `blocked` / `warning` / `ready` |
| `defaultProviderId` | 当前默认服务商 |
| `defaultProviderName` | 当前默认服务商名称 |
| `defaultModelId` | 当前默认模型 |
| `defaultModelName` | 当前默认模型名称 |
| `lastProviderTest` | 最近服务商连通性测试 |
| `lastModelTest` | 最近模型调用测试 |
| `message` | 面向用户的简短说明 |
| `actionLabel` | 推荐按钮文案 |
| `actionTarget` | 推荐跳转位置 |

### 15.4 状态文案

| 状态 | 工作台提示标题 | 说明 | 主按钮 |
| --- | --- | --- | --- |
| `no_provider` | 尚未连接模型服务商 | 请先连接 DeepSeek、MiMo、OpenAI 或自定义服务商。 | 连接服务商 |
| `provider_missing_key` | 服务商缺少 API Key | 已创建服务商，但还不能发起请求。 | 补充 API Key |
| `no_model` | 尚未选择可用模型 | 服务商已连接，请选择或同步一个模型。 | 选择模型 |
| `no_default_model` | 尚未选择默认模型 | 已有模型，但系统不知道默认使用哪一个。 | 设置默认模型 |
| `not_tested` | 模型尚未测试 | 配置已完成，建议先测试模型调用。 | 测试模型 |
| `test_failed` | 模型调用测试失败 | 请查看失败原因并修正 API Key、Base URL、模型名或参数。 | 查看失败原因 |
| `ready` | 模型配置可用 | 当前模型可用于启动任务。 | 配置 |

### 15.5 不允许的兜底文案

只要系统已经检测到任意服务商或模型，就不要再笼统显示：

```text
模型未配置，无法启动任务
```

应改为具体状态，例如：

```text
尚未选择默认模型
```

```text
模型调用测试失败
```

```text
服务商缺少 API Key
```

### 15.6 刷新逻辑

工作台必须在以下时机刷新模型配置状态：

- 首次进入工作台。
- 从模型配置页返回工作台。
- 用户切换工作区。
- 用户设置默认模型后。
- 用户完成服务商测试或模型调用测试后。
- 用户点击“重新检查”按钮后。

不能只在选择工作区时刷新，否则会出现用户已经配置模型，但工作台仍显示未配置的情况。

## 18. 开发任务拆解

### P0：必须先改

- 首配向导第 3 步改为“选择推荐模型 + 测试”，不要出现手写模型表单。
- 内置服务商选择后必须生成推荐模型列表。
- 默认配置路径移除 Provider ID、Model ID、capabilities、contextWindow 输入。
- DeepSeek / MiMo 作为内置服务商，支持 OpenAI-compatible 调用和流式输出。
- 连接失败和保存失败展示具体原因，并保留表单内容。
- 明确参数分层：应用级单模型高级参数、项目级单模型高级参数、使用场景参数。
- 工作台模型配置状态拆分，不能只显示“模型未配置”。

### P1：体验修正

- 使用场景固定为：需求理解、任务规划、任务执行、结果检查、总结归档。
- 使用场景区域不要出现 Binding、role、AI 角色等描述。
- 每个模型的高级调用参数需要真实保存和读取。
- 每个项目可以覆盖单模型高级参数，并随项目迁移。
- 使用场景支持继承默认模型和覆盖模型 / 参数。
- 模型能力改为中文只读标签，高级自定义模型用复选框。

### P2：高级能力

- 增加远端模型列表同步。
- 增加模型调用测试和流式输出测试。
- 增加导入 / 导出配置。
- 增加项目配置导入时的服务商 / 模型映射提示。
- 增加原始 JSON 预览。
- 增加更完整的 provider 协议高级配置。

## 19. 验收标准

### 19.1 服务商配置

- 配置 DeepSeek / MiMo / OpenAI 时不出现 Provider ID 输入框。
- 内置服务商自动填充 Base URL。
- API Key 是默认视图中唯一必须手动填写的连接凭证。
- 服务商连通性失败能看到具体原因。

### 19.2 模型配置

- 内置服务商选择后立即看到推荐模型。
- 默认流程不要求手写 Model ID。
- 默认流程不要求手写 Model Name。
- 默认流程不要求手写 capabilities。
- 默认流程不要求手写 contextWindow。
- 模型以卡片或下拉选择方式呈现。
- 自定义模型入口在高级设置。
- 每个模型可以配置自己的高级调用参数。

### 19.3 调用参数

- 页面提供默认调用参数配置。
- 至少支持 `temperature`、`top_p`、`max_tokens`、`stream`、`timeout_ms`、`retry_count`。
- 支持模型能力相关参数的启用 / 禁用说明。
- 支持应用级单模型高级参数。
- 支持项目级单模型高级参数覆盖。
- 支持使用场景覆盖参数。
- 参数修改后刷新页面仍能保留。

### 19.4 使用场景

- GUI 中不出现 Binding 作为主概念。
- 默认视图不出现 role、scope、priority。
- 使用场景固定为：需求理解、任务规划、任务执行、结果检查、总结归档。
- 每个场景可以继承默认模型。
- 每个场景可以选择独立模型。
- 每个场景可以覆盖调用参数。

### 19.5 项目可移植性

- 项目配置可以独立保存模型选择和参数覆盖。
- 导出项目配置不包含 API Key。
- 导入项目配置时，如果本机缺少服务商或模型，能提示映射或重新选择。
- 同一个模型在不同项目中可以有不同高级参数。

### 19.6 工作台状态展示

- 没有服务商时显示“尚未连接模型服务商”。
- 有服务商但缺 API Key 时显示“服务商缺少 API Key”。
- 有服务商但没有模型时显示“尚未选择可用模型”。
- 有模型但没有默认模型时显示“尚未选择默认模型”。
- 有默认模型但未测试时显示“模型尚未测试”。
- 最近测试失败时显示“模型调用测试失败”和具体失败原因。
- 模型可用时显示当前服务商 / 模型摘要。
- 从模型配置页返回工作台后，状态必须刷新。

### 19.7 测试与错误

- 服务商连通性测试和模型调用测试分开。
- 模型调用测试能验证当前模型名是否可用。
- `stream` 开启时能验证流式输出。
- 失败时展示 HTTP 状态码、检查地址、响应摘要或可理解错误。
- 保存失败后仍可编辑并再次保存。

### 19.8 高级设置

- ID、scope、priority、auth header、paths 等字段放在高级设置。
- 高级设置默认折叠。
- 高级设置不影响默认配置流程。

## 20. 一句话结论

模型配置页不应是 Provider / Model / Binding 三张表的编辑器。

它应该是：

```text
服务商连接 + 模型选择 + 调用参数 + 使用场景路由
```

当前页面方向已经接近，但首配向导、字段暴露、测试拆分、使用场景命名、单模型高级参数配置、项目级高级参数覆盖和可移植性必须继续修正后，才能作为开发实现依据。
